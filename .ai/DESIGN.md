# Design and UI Guidelines

This document governs the visual layer, component design, and user experience of the application.

---

## Core Tools & Ecosystem

* **CSS Framework:** [TailwindCSS v4](https://tailwindcss.com/docs) (utilizing modern `@theme` variables and utility classes).
* **UI Component Library:** [Shadcn UI](https://ui.shadcn.com/) (targeting Svelte 5 / Astro).
* **Icons:** Lucide Icons (`lucide-svelte` / `lucide-astro`).

---

## Modality Component & Island Rules

### 1. Website Modality (Astro Islands)
In Astro, all components render to **static HTML with zero JavaScript** by default.
* **Static Elements:** Always build heroes, cards, layouts, and typography directly as `.astro` components.
* **Interactive Elements:** When client-side state is required (e.g. mobile drawer menu, dropdown, interactive filter), build it as a Svelte 5 component (`.svelte`).
* **Mandatory Client Directives:** You **MUST** pass an explicit client directive in Astro pages/layouts. Never import an interactive Svelte component without one:
  ```astro
  ---
  import Navbar from '../components/Navbar.svelte';
  import SearchDialog from '../components/SearchDialog.svelte';
  ---
  <!-- Critical above-the-fold interactivity: loads immediately -->
  <Navbar client:load />

  <!-- Lower priority interactivity: loads when browser is idle -->
  <SearchDialog client:idle />
  ```
  * `client:load`: For critical navigation, drawers, or mobile menus above the fold.
  * `client:idle`: For search modals, theme switchers, or lower-priority interactive widgets.
  * `client:visible`: For carousels or interactive components located further down the page.

### 2. Application Modality (SvelteKit)
* All components are Svelte 5 components using Runes (`$state`, `$derived`, `$props`).
* Render client and server components natively within SvelteKit routing without Astro client directives.

## UI/UX Rules & Accessibility Guardrails

1. **Mobile-First Responsiveness:**
   - Always design from mobile screens (`< 768px`) upwards using Tailwind breakpoints (`md:`, `lg:`, `xl:`).
   - Touch targets for interactive elements (buttons, links, toggles) must meet a minimum size of 44x44px on mobile devices.

2. **Theming & Color Schemes:**
   - Support light and dark modes natively using Tailwind theme tokens (e.g., `bg-background text-foreground`).
   - Use CSS variables for design token alignment between Shadcn and custom components.

3. **Accessibility (a11y):**
   - Strictly employ semantic HTML elements (`<header>`, `<nav>`, `<main>`, `<article>`, `<button>`).
   - Maintain accessible ARIA attributes on modals, accordions, and dropdown menus. Do not alter or strip default accessibility features provided by Shadcn UI components.
   - Maintain a minimum contrast ratio of 4.5:1 for standard text and 3:1 for large text.

4. **Component Architecture:**
   - All custom UI components must be saved as `PascalCase.svelte` or `PascalCase.astro`.
   - Keep components presentation-focused; delegate shared state to universal Svelte 5 `.svelte.ts` modules.

5. **Brand Alignment & Copy Blueprint:**
   - All component labels, headings, CTA buttons, and marketing sections must adhere to the tone of voice and information architecture defined in [`.ai/MANIFESTO.md`](.ai/MANIFESTO.md). Never invent arbitrary copy when `.ai/MANIFESTO.md` provides approved messaging.

## Skill Integration Protocol: High-End Design & Web QA

This protocol governs the dual-phase execution of visual design and technical quality auditing to prevent conflicting design goals.

### 1. Phase 1: Generation (`high-end-visual-design`)
* **Source:** `https://github.com/leonxlnx/taste-skill` (`--skill high-end-visual-design`)
* **Trigger Rule:** Activate this skill **ONLY** when initiating a new design, building components, prototyping, or writing UI code from scratch.
* **Role:** The single source of truth for art direction, typography pairings, micro-interactions, and premium layout structure.
* **Restriction:** Never invoke this skill to review existing functional code unless explicitly instructed to perform a complete "aesthetic redesign."

### 2. Phase 2: Audit (`web-design-guidelines`)
* **Source:** `https://github.com/vercel-labs/agent-skills` (`--skill web-design-guidelines`)
* **Trigger Rule:** Activate this skill **STRICTLY** during the review and QA phases.
* **Role:** Technical auditor for accessibility (a11y), semantic HTML structure, spacing consistency, and usability standard compliance.
* **Restriction:** Do not use this skill to make foundational visual or styling decisions. It must only run *after* Phase 1 generation is complete.

### 3. Conflict Resolution (Aesthetics vs. Accessibility)
When the Audit skill flags an issue in the code generated by the Generation skill, apply these specific resolution rules to prevent breaking the premium aesthetic:

* **Contrast Conflicts:** If the auditor rejects a subtle text color for failing WCAG contrast ratios, DO NOT revert to a standard, harsh solid gray. Adjust the opacity (e.g., shifting from `text-white/40` to `text-white/70`) or tweak the lightness while strictly maintaining the original premium color palette.
* **Border Restrictions:** If the auditor requests visible borders to define component boundaries, **MAINTAIN the Phase 1 ban** on standard solid 1px gray lines. Resolve the boundary issue by using multi-layered soft shadows, glassmorphism effects (backdrop blur), or ultra-low opacity borders (e.g., `border-white/10` or `border-black/5`).
* **Focus States (a11y):** The auditor will demand `:focus-visible` states for keyboard navigation. Always implement them, but adapt them to the Phase 1 aesthetic. Use faded focus rings with smooth transitions (e.g., `focus-visible:ring-2 focus-visible:ring-brand-accent/30 transition-all duration-300`), strictly avoiding raw browser-default blue outlines.

### 4. Ideal Workflow (Prompt Template)
To execute both skills smoothly in a single AI generation without crossing their logic, use this structured execution flow when prompting the agent:

> **Objective:** Build [INSERT COMPONENT/WEB PAGE].
>
> **Step 1: Generation**
> Use `high-end-visual-design` to construct the layout, styling, and micro-interactions in Astro / Svelte 5 / TailwindCSS v4. Apply premium aesthetics, cinematic animations, and typography rules. Do not stop until the full UI structure is complete.
>
> **Step 2: Audit & Refine**
> Once Step 1 is fully coded, act as QA using `web-design-guidelines` to audit the generated output. Fix any missing `aria-labels`, semantic tags, and focus states. You must apply these accessibility fixes while strictly respecting the "Conflict Resolution" rules to preserve the premium aesthetic.
